How to read these examples

Each card names a business workflow, maps it to a simple public state-transition statement, and tells you what the receipt proves. If your real workflow needs a custom predicate or private-input handling, use the example only to start the design discussion.

Use the statement

The statement is the public claim a verifier can check. For the live template, it is always an additive transition.

Generate the receipt

The playground can mint a live receipt for each sample statement through the anonymous demo path.

Keep the boundary

The receipt proves the encoded arithmetic transition, not real-world facts, private data, or unsupported program semantics.

AgentsMCP

Agent approval counter

An agent supervisor tracks approved actions during a session and returns a receipt with the final checkpoint.

Initial42
Deltas3, 2, 5
Final52

Proves

  • The public approval counter advanced from 42 to 52 by the declared increments.
  • A downstream service can verify without replaying the agent transcript.

Does not prove

  • That each real-world approval was correct.
  • That private approval details stayed hidden.
{
  "template_id": "accumulator_step",
  "params": {"initial": 42, "final": 52, "deltas": [3, 2, 5]}

Use examples in evaluation

  • Pick the card closest to your workflow.
  • Generate the live receipt in the playground.
  • Copy the verifier result into your evaluation packet.
  • Replace the sample statement with your real public parameters before production.

Escalate beyond examples when

  • The statement is not additive or accumulator-shaped.
  • The workflow needs private-input handling.
  • The receipt must be verified on-chain or in a restricted runtime.
  • The trace length needs Compute sizing or reserved capacity.

Examples should become live receipts, not slideware.

Start from one sample, generate a receipt, verify it, and then decide whether your actual workflow has the same proof boundary and business value.
