Who should run a pilot

The best pilots start where a receipt changes trust, sales, or operations. If the workflow only needs a log line, use a log line. If a recipient needs to verify a transition without replaying your system, TinyZKP is worth testing.

Agents

Agent actions with consequences

Receipt tool-call batches that move balances, update records, change permissions, reconcile ledgers, or finalize customer-visible workflow state.

Platforms

The 14-day pilot shape

A strong pilot is deliberately narrow. It should prove one workflow, expose the receipt where the recipient will actually see it, and produce a clear next commercial step.

What to bring

  • The workflow name and the state transition you want the receipt to prove.
  • Example public parameters, expected trace size, and proof frequency.
  • Who verifies the receipt and where the verifier result should appear.
  • Any privacy, retention, procurement, support, or latency constraints.

What not to ask the pilot to prove

  • Real-world truth that is not encoded into the statement.
  • Generic private-input zero knowledge without a documented template.
  • Arbitrary zkVM, zkML, rollup, or on-chain verifier support as if already live.
  • Sub-second proofs for every UI interaction.

Start with one receipt that matters.

A good pilot creates a durable trust artifact: a receipt URL, verification result, cost model, and rollout decision. Keep the scope small enough to ship, but important enough that verification changes the product conversation.
