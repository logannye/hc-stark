Receipt, not replay

A TinyZKP receipt is a proof object for a state change.

Receipts are the distribution format for trust. Your service or agent mints a receipt once, attaches it to an output, and any recipient can verify the encoded transition without replaying the source system.

Why receipts work

Portable

A receipt can be stored beside a row, returned from an API, linked in an agent output, or sent to an auditor.

Machine-checkable

The verifier checks proof bytes and statement metadata. It does not need your database, logs, or agent transcript.

Explicitly scoped

The receipt proves the encoded statement, not off-chain facts or private-input claims that were not part of the template.

Receipt anatomy

{
  "template": "accumulator_step",
  "statement": {
    "initial": 1000,
    "final": 1045,
    "deltas": [10, 20, 15]
  },
  "proof": {
    "version": 5,
    "bytes": [106, 143, "..."]
  }
}

Lifecycle

  • Mint: submit a template request and receive a job ID.
  • Poll: fetch the completed proof object.
  • Attach: store or return the receipt with the state-changing output.
  • Verify: use the public verifier, API verifier, SDK, CLI, or compatible WASM package.

Good receipt targets

  • Agent tool-call batches
  • Ledger and balance checkpoints
  • Audit-log accumulators
  • Reserve or liability aggregate updates
  • Long state-transition traces
