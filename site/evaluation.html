Evaluation kit

Decide whether proof receipts belong in your product.

TinyZKP should be evaluated on one consequential state transition: an agent action, API mutation, audit checkpoint, reserve update, or long trace where a recipient needs proof without replaying the source system. Use this kit to align engineering, security, finance, procurement, and the business owner before buying.

The question to answer

Do not evaluate TinyZKP as generic cryptography. Evaluate whether a portable receipt changes the trust boundary for one workflow.

Workflow

What state changes?

Name the action, checkpoint, mutation, or trace. If there is no meaningful state transition, TinyZKP is probably the wrong first tool.

Verifier

Who checks it?

Identify the customer, auditor, downstream service, supervisor agent, or internal reviewer that benefits from verification without replay.

Receipt

What will they see?

Decide where the receipt URL, proof object, badge, or agent receipt envelope appears in the product workflow.

30-minute evaluation path

A strong evaluation produces evidence, not a vague proof-of-concept. Move through these five steps before involving procurement or reserved capacity.

00-05Choose one workflow and name the verifier who should trust the receipt.
05-10Check whether the statement fits the live template or needs pilot review.

18-25Estimate volume, trace size, plan fit, and whether Compute or self-serve pricing applies.
25-30Choose a route: start free, use Developer or Pro, run a pilot, or defer.

Decision criteria

Use these checks to avoid buying a proof system for a problem that a signature, log, or hash chain already solves.

Go

Verifier needs independence

A recipient needs to verify a state transition without trusting your database, logs, screenshots, or agent transcript.

Go

Receipt can travel

The receipt can be returned in an API response, agent output, audit record, badge, or customer-facing page.

Go

Cost replaces work

Proof generation replaces replay, manual audit exports, high-RAM prover operations, dispute handling, or repeated evidence requests.

Review first

Custom statement

The workflow is valuable but not covered by the live template. Use pilot review to design the statement and verifier path.

Review first

Private-input need

Do not put secrets into transparent receipt parameters. Private-input claims require a documented, template-specific review path.

No-go

No external verifier

If everyone already trusts your service and no one will inspect the receipt, start with signed logs, metrics, or audit trails instead.

ROI drivers

TinyZKP becomes profitable for a customer when one receipt removes recurring coordination, infrastructure, review, or support cost.

Reduce replay and audit labor

A compact receipt lets a reviewer check the encoded transition without gaining access to the source system or asking engineering to reconstruct state.

Make agent actions accountable

Receipts give agent outputs a machine-checkable artifact that can be stored beside approvals, fund movements, record updates, and workflow checkpoints.

Avoid prover infrastructure

Compute shifts long supported traces away from high-RAM workers, custom queues, segmentation, and on-call ownership.

Shorten sales and procurement

Public trust, pricing, schema, OpenAPI, changelog, and evaluation metadata reduce the number of bespoke review emails needed before a pilot.

Go if

  • A real recipient benefits from checking the receipt.
  • The workflow can be encoded as a supported state transition or scoped pilot.
  • Transparent public parameters are acceptable for the first rollout.
  • The cost model is clearer than replay, manual evidence, or prover operations.

Pause if

  • The statement is really a private-input requirement without a reviewed template.
  • The team wants generic zkVM, zkML, rollup, or on-chain verifier availability as if it is live today.
  • The proof would not be attached to any customer, auditor, agent, or system-facing artifact.
  • The buyer needs contractual support before the workflow and verifier path are clear.

The best evaluation creates one receipt a buyer cares about.

Start with a real state transition, a named verifier, a visible receipt, a cost estimate, and a clear go/no-go decision. Everything else should wait until that first trust boundary is proven.
