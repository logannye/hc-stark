Security status

Transparent receipt claims, explicit audit boundaries.

TinyZKP's live public product is a transparent STARK state-transition receipt service. The verifier floor rejects legacy pre-v5 proofs, the default receipt is not marketed as input privacy, and templates stay hidden until their predicate is enforced and their review status is appropriate for production exposure.

For procurement questionnaires and buyer-facing review material, start with the Trust Center or use the Security Review Packet.

Current production scope

Template discovery uses three lifecycle values: live, audit_gated, and preview. Only live templates are listed and dispatchable in the default production deployment.

Live

accumulator_step

Transparent state-transition receipts: starting from X, applying public deltas reaches Y. Verification can run through the API, SDKs, MCP, CLI, or browser verifier.

Audit gated

General AIR templates

Some templates may be implemented on the v7 general-AIR path, but remain hidden from default production listings until external audit coverage is complete.

Preview

zkML, Spartan, custom predicates

Preview or structure-only workloads are not part of the self-serve production promise unless explicitly enabled for development or a private design-partner engagement.

Do not treat default TinyZKP receipts as input privacy. The default self-serve receipt is transparent attestation. Privacy-oriented flows require a separately documented template, configuration, and audit status.

Responsible disclosure

For suspected vulnerabilities in proof verification, API authentication, billing, tenant isolation, SDK packages, or the browser verifier, email logan@tinyzkp.com. Include the affected surface, reproduction steps, proof bytes or request IDs where relevant, and whether the issue affects confidentiality, soundness, billing, or availability.

  • Do not test against other users' accounts or data.
  • Do not run high-volume denial-of-service testing against the hosted service.
  • Proof-system reports should include the proof version and verifier package used.
