OpenAI-powered agent workflows

Return proof receipts with important tool results.

OpenAI-powered agent applications can call tools, orchestrate workflows, and return structured outputs. TinyZKP fits after the state-changing tool call: your backend proves the supported transition, then the agent returns the result plus a receipt URL that another human, service, or agent can verify.

Backend tool pattern

Keep proof generation in your server-side tool implementation. The agent should receive a structured result that includes the business output, proof statement, receipt URL, and verifier URL.

async function finalizeCheckpoint(input) {
  const businessResult = await updateState(input);
  const receipt = await tinyzkp.proveTemplate("accumulator_step", {
    initial: input.initial,
    final: businessResult.final,
    deltas: businessResult.deltas
  });
  return {
    result: businessResult,
    receipt_url: receipt.verify_url,
    proof_boundary: "initial + sum(deltas) = final"
  };
}

Agent output contract

Use structured output so the receipt is not buried in prose. Downstream systems should be able to parse the result, verify the receipt, and understand the boundary.

{
  "action": "checkpoint_finalized",
  "status": "succeeded",
  "receipt_url": "https://tinyzkp.com/verify#proof=...",
  "verifier": "https://tinyzkp.com/verify",
  "proof_boundary": "encoded state transition only"
}

OpenAI's current developer docs include Agents SDK, tool use, structured output, and MCP/connectors surfaces. TinyZKP should sit behind the tool boundary or connector layer, not inside prompt-only reasoning.

Best first OpenAI-powered workflows

Customer-visible tool results

Return a receipt when an agent updates a quota, balance, entitlement, workflow checkpoint, or visible status.

Supervisor-agent verification

Have a second agent verify receipts before relying on another agent's output in a chain of work.

Audit and support evidence

Store receipts beside support tickets, review logs, and operational checkpoints so teams can verify without replay.

Use TinyZKP when

  • The tool mutates durable state.
  • A customer, auditor, service, or supervisor agent will rely on the result.
  • Manual replay would be slow or unavailable.
  • The proof statement fits a supported template or a reviewed pilot path.

Skip TinyZKP when

  • The answer is draft prose or brainstorming.
  • No one will inspect the receipt.
  • The needed claim is not encoded by the proof statement.
  • The workflow requires unsupported private-input or arbitrary program proofs.

Buying path

Use Free for evaluation, Developer for one backend tool, Pro when receipts become recurring and visible, and pilot review when statement design or verifier placement needs a production decision.
