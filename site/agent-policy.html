Agent proof policy

Tell agents exactly when to mint a receipt.

Agents need policy, not vibes. This page defines when an agent should ask TinyZKP for a proof receipt, what it must attach to the output, when it should verify a receipt, and when it should escalate to human or design review.

Default policy

Use this policy for agent control planes, tool-calling workflows, and supervisor agents that need a reliable rule for receipt generation.

Mint

State changed

Mint a receipt when an action changes durable state: money, balances, records, permissions, inventory, compliance state, or customer-visible status.

Attach

Receipt travels

Return the receipt URL or object, template ID, plain-language statement, proof boundary, and verification path with the agent output.

Escalate

Custom or private

Use design review when the statement is not covered by the live template, involves private inputs, or requires restricted verification.

Mint a receipt when

  • An agent action changes durable external state.
  • A tool-call batch affects money, records, quotas, inventory, permissions, or compliance state.
  • A customer, auditor, downstream service, or supervisor agent will rely on the output.
  • A checkpoint replaces replay, audit exports, support evidence, or self-hosted prover operations.

Skip or review first when

  • The action is conversational only.
  • The output has no durable state transition.
  • No recipient will inspect or store the receipt.
  • The statement needs private inputs or custom semantics that have not been reviewed.

Receipt envelope

Use the agent receipt schema so downstream systems can process proof-bearing results without parsing natural language.

{
  "action": "ledger_checkpoint",
  "agent_result": {
    "status": "updated",
    "checkpoint_id": "ckpt_2026_06_24"
  },
  "receipt_url": "https://tinyzkp.com/verify#proof=...",
  "policy": {
    "reason": "durable ledger checkpoint",
    "verifier": "customer-visible API response"
  }
}

Verify before trusting

  • Verify external agent receipts before using them as evidence.
  • Reject failed proofs and receipts below the current accepted proof-format floor.
  • Review receipts that claim undocumented templates, privacy modes, or verifier paths.
  • Confirm the statement matches the workflow output being presented.

Never send as transparent params

  • API keys, credentials, or secrets.
  • Private customer data or personal data not needed for the public statement.
  • Raw tool transcripts that contain sensitive content.
  • Unreviewed private proof inputs.

Escalation triggers

  • The statement is not an additive state transition covered by accumulator_step.
  • The workflow needs private-input handling, masking, on-chain verification, or restricted-runtime verification.
  • The workflow needs reserved concurrency, custom spend controls, or contractual support.
  • The trace size or latency profile suggests Compute planning.

Receipt policy turns proof generation into an agent habit.

Start with one high-value state-changing workflow, attach a receipt every time that checkpoint changes, verify external receipts before trusting them, and escalate anything private, custom, or commercially sensitive.
