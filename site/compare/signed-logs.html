TinyZKP receipts vs signed logs.

A signed log is a strong accountability primitive: it proves who wrote a record and whether the bytes changed. A TinyZKP receipt answers a different question: did the encoded transition from old state to new state satisfy the declared rule?

Use both when the action matters

QuestionSigned logTinyZKP receipt
Who wrote it?Yes, if key management is sound.Not the primary claim; pair with signatures for identity.
Was the record edited?Yes, the signature fails if bytes change.Receipt bytes are also tamper-evident, but statement validity is the core value.
Was the transition valid?No. A bad transition can still be signed.Yes, for the supported template and encoded statement.
Does the verifier need the source system?Often needs log context and replay logic.No replay of the source workflow is required.

Use signed logs when

  • You need authorship and tamper evidence.
  • The verifier already trusts the application logic.
  • Replaying the action is cheap and easy.

Use TinyZKP when

  • The verifier needs proof that the transition rule was followed.
  • The source system is unavailable or should not be replayed.
  • An agent, auditor, or counterparty needs a portable receipt.
