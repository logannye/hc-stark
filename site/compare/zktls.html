Comparison

TinyZKP receipts vs zkTLS.

zkTLS and TinyZKP solve different verification problems. zkTLS is strongest when a user needs to prove something about data received from a website. TinyZKP is strongest when a service or agent needs to prove that an encoded state transition followed a supported rule.

Use the right proof source

QuestionzkTLSTinyZKP
Where does the fact come from?A TLS session with a web service or issuer.Your encoded state-transition statement and proof template.
What is the verifier checking?That a statement reflects data from a web interaction, subject to the zkTLS trust model.That the receipt's public transition satisfies the supported proof rule.
Best examplesAccount status, credential facts, web data provenance, consented user data.Agent tool batches, API mutations, audit checkpoints, ledger aggregates, long traces.
How they combineCan supply source facts for a workflow.Can receipt the later transition or checkpoint that used those facts.

Choose zkTLS when

  • The core question is whether web data came from a source.
  • The user consents to proving a fact from an account or session.
  • Your workflow depends on external web data provenance.

Choose TinyZKP when

  • The core question is whether a state transition was valid.
  • The receipt should attach to an agent output, API response, or audit checkpoint.
  • The verifier should not replay your source system.

Complementary, not interchangeable

A future agent workflow may use zkTLS to prove an external fact, then use TinyZKP to receipt a downstream state transition that consumed that fact. The website should avoid claiming TinyZKP replaces zkTLS; the sharper position is that TinyZKP standardizes the receipt for the state change.
