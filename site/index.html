Proof Scope

What a TinyZKP receipt proves, and what it does not

Clear boundaries make this product easier to trust, buy, and integrate.

Production self-serve receipts prove

  • A declared state-transition chain is internally consistent.
  • The public accumulator_step template moved from initial value to final value via the declared deltas.
  • The proof bytes satisfy the current production verifier format.
  • A recipient can verify the receipt without calling your system.

They do not automatically prove

  • Private-input zero knowledge for every workload.
  • The off-chain business truth of events that were never encoded into the statement.
  • General zkVM, zkML, rollup, or smart-contract verifier availability.
  • External cryptographer audit completion; the current audit boundary is public.

How It Works

Three steps to a verifiable receipt

Prove a state transition is valid — that a declared sequence of steps moves from a known start to a known end — so anyone can verify it without re-running it.

1

Submit

POST to /prove/template/accumulator_step with your parameters, or call the same action through MCP. You get a job ID instantly.

2

Prove

Our servers generate a ZK-STARK proof using O(√N) memory, where N is the size of the computation. No trusted setup. No ceremony. Typical proofs complete in 1–5 seconds.

3

Verify

Anyone can verify the receipt via /verify. Always free. The verifier checks the encoded statement without replaying your system.

Get Started in 5 Lines

Python, TypeScript, or plain curl. Your first proof is free.

from tinyzkp import TinyZKP

async with TinyZKP("https://api.tinyzkp.com", api_key="tzk_...") as client:
    job_id = await client.prove_template("accumulator_step", params={"initial": 1000, "final": 1045, "deltas": [10, 20, 15]})
    proof  = await client.wait_for_proof(job_id)
    result = await client.verify(proof)  # free!
import { HcClient } from "tinyzkp";

const client = new HcClient("https://api.tinyzkp.com", { apiKey: "tzk_..." });
const jobId  = await client.proveTemplate("accumulator_step", { initial: 1000, final: 1045, deltas: [10, 20, 15] });
const proof  = await client.waitForProof(jobId);
const result = await client.verify(proof);  // free!
# Submit a proof via template (recommended)
curl -X POST https://api.tinyzkp.com/prove/template/accumulator_step \
  -H "Authorization: Bearer tzk_..." \
  -H "Content-Type: application/json" \
  -d '{"params":{"initial":1000,"final":1045,"deltas":[10,20,15]}}'
# {"job_id":"a1b2c3d4-e5f6-7890-abcd-ef1234567890"}

# Poll for result
curl https://api.tinyzkp.com/prove/a1b2c3d4-e5f6-7890-abcd-ef1234567890 \
  -H "Authorization: Bearer tzk_..."

# Verify through the hosted API (free; auth prevents abuse)
curl -X POST https://api.tinyzkp.com/verify \
  -H "Authorization: Bearer tzk_..." \
  -H "Content-Type: application/json" \
  -d '{"proof":{...}}'

FAQ

The answers skeptical developers look for first

Is TinyZKP actually zero-knowledge?

The public self-serve product is a transparent STARK state-transition receipt. Privacy-oriented flows require a separately documented template, configuration, and audit status.

Can verification happen without re-running my system?

Yes. The verifier checks the receipt object itself. The public page is WASM-first and falls back to the hosted verifier when the local package is behind the current production format.

What proof version should I integrate?

Use current protocol v5 receipts from the hosted API. Production verification rejects pre-v5 receipts.

When should I choose Compute?

Choose Compute when long state-transition traces would otherwise force high-RAM prover hardware, segmentation, recursion, or operational overhead.

Generate a receipt now, or size a serious workload.

The self-serve path is built for transparent state-transition receipts. Custom state machines, very large traces, zkVM, zkML, and rollup work should start as design-partner conversations.
