Quickstart

Get from zero to a verified state-transition receipt in four steps. No cryptography knowledge required.

1

Get an API key

Sign up for a free account (100 proofs/month, no credit card). Your API key (tzk_...) will be emailed instantly.

2

Submit a proof

Use a live proof template to prove a chain of state transitions. This example proves that starting from 1000 and applying the deltas [10, 20, 15] reaches 1045.

curl 
curl -X POST https://api.tinyzkp.com/prove/template/accumulator_step \
  -H "Authorization: Bearer tzk_..." \
  -H "Content-Type: application/json" \
  -d '{"params":{"initial":1000,"final":1045,"deltas":[10,20,15]}}'

Response:

// Save the job_id — you'll need it next. job_id is a UUID.
{"job_id":"a1b2c3d4-e5f6-7890-abcd-ef1234567890"}
3

Poll until complete

Proof generation takes 1–5 seconds. Poll the job ID until status is "succeeded":

curl 
curl https://api.tinyzkp.com/prove/a1b2c3d4-e5f6-7890-abcd-ef1234567890 \
  -H "Authorization: Bearer tzk_..."

Response when done:

// proof.bytes is a JSON array of unsigned bytes (Vec<u8>), not a hex string.
{"status":"succeeded","proof":{"version":5,"bytes":[106,143,59,44,...]}}

Status values are one of "pending", "running", "succeeded", or "failed". Keep polling while it’s pending or running; when it’s succeeded, copy the entire proof object. On failed the response includes an error string.

4

Verify the proof

Pass the proof object from step 3 to the verify endpoint. Verification is always free — no charge. Auth is required only to prevent abuse.

curl 
curl -X POST https://api.tinyzkp.com/verify \
  -H "Authorization: Bearer tzk_..." \
  -H "Content-Type: application/json" \
  -d '{"proof":{"version":5,"bytes":[106,143,59,44,...]}}'

Response:

// The verifier confirmed the state-transition receipt.
// On failure, error contains a human-readable message.
{"ok":true,"error":null}

WASM-First Verification

Verify compatible receipts locally with the @tinyzkp/verify WASM package. No API key is required for verification. The hosted public verifier tries this WASM path first and falls back to TinyZKP's verifier endpoint when the local package is behind the current production proof format.

install 
npm install @tinyzkp/verify

Browser

JavaScript 
import init, { verify } from '@tinyzkp/verify';

await init();  // load WASM binary (~785 KB)

const result = verify({ version: 5, bytes: proofBytes });
console.log(result.ok);     // true
console.log(result.version); // 5

Node.js

JavaScript 
const { verify_json } = require('@tinyzkp/verify');

const result = verify_json(JSON.stringify(proofObject));
console.log(result.ok); // true
  • Local verification path — no network request for receipt formats supported by the bundled WASM package
  • Edge-compatible — runs in Cloudflare Workers, Deno, Vercel Edge Functions
  • ~785 KB WASM binary (gzips to ~300 KB)
  • Returns { ok: bool, error?: string, version?: number }

Authentication

All endpoints (including /verify) require a Bearer token in the Authorization header:

Authorization: Bearer tzk_...
  • Your API key is delivered via email after signing up.
  • The /verify endpoint is free (no charge) but requires your API key to prevent abuse.
  • Keep your API key secret. Do not expose it in client-side code or public repositories.

Magic-Link Sign-In

If you lose access to your API key, request a one-time magic link by email. The link unlocks your account dashboard, where you can recover or rotate the key. Both routes are Cloudflare Pages Functions on tinyzkp.com, not on api.tinyzkp.com. The send route is rate-limited to 3 requests per IP per 10 minutes.

curl — request the link 
curl -X POST https://tinyzkp.com/api/send-magic-link \
  -H "Content-Type: application/json" \
  -H "Origin: https://tinyzkp.com" \
  -d '{"email": "you@example.com"}'

Always returns {"ok": true} on success (regardless of whether the email exists, to prevent account enumeration). The user clicks the link, which redirects to tinyzkp.com/account?token=.... The account page then exchanges the token for credentials:

curl — verify the token 
curl -X POST https://tinyzkp.com/api/verify-magic-link \
  -H "Content-Type: application/json" \
  -H "Origin: https://tinyzkp.com" \
  -d '{"token": "TOKEN_FROM_EMAIL"}'

Returns the tenant’s credentials so the dashboard can resume the session. Tokens are single-use and expire quickly. You typically don’t need to call these directly — the account dashboard drives the full flow.

Key Rotation

Rotate your API key at any time. Your old key is immediately invalidated and a new key is returned. Limited to once per 24 hours. The rotation route lives on tinyzkp.com (a Cloudflare Pages Function), not on api.tinyzkp.com.

curl 
curl -X POST https://tinyzkp.com/api/rotate-key \
  -H "Authorization: Bearer tzk_YOUR_CURRENT_KEY"

Response:

{
  "api_key": "tzk_NEW_KEY_HERE...",
  "prefix": "tzk_a3b2...",
  "message": "Key rotated successfully. Your old key is now invalid."
}

Proof Templates

TinyZKP provides a live template for transparent state-transition receipts. Templates handle the cryptographic complexity — you provide the transition parameters. Use POST /prove/template/:id to prove, or browse templates with GET /templates. More proof types are in development and remain gated until deployed, documented, and assigned explicit review status.

TemplateLifecycleWhat It Proves (Plain English)Key Parameters

Template Examples

The example below is a complete, copy-paste working example. Replace tzk_... with your API key and run.

The Python and TypeScript snippets use the official TinyZKP HTTP-API client SDKs. Install once, then any subsequent example just works:

install

accumulator_step — prove a chain of state transitions

Proves that applying a sequence of additive deltas to initial reaches final. Use for balance updates, ledger reconciliation, or audit-log checkpoints.

curl 
curl -X POST https://api.tinyzkp.com/prove/template/accumulator_step \
  -H "Authorization: Bearer tzk_..." \
  -H "Content-Type: application/json" \
  -d '{"params":{"initial":1000,"final":1045,"deltas":[10,20,15]}}'
Python 
from tinyzkp import TinyZKPSync
with TinyZKPSync("https://api.tinyzkp.com", api_key="tzk_...") as c:
    job = c.prove_template("accumulator_step", params={"initial":1000,"final":1045,"deltas":[10,20,15]})
    proof = c.wait_for_proof(job)
    assert c.verify(proof).ok
TypeScript 
import { TinyZKP } from "tinyzkp";
const c = new TinyZKP("https://api.tinyzkp.com", { apiKey: "tzk_..." });
const job = await c.proveTemplate("accumulator_step", { initial:1000, final:1045, deltas:[10,20,15] });
const proof = await c.waitForProof(job);
console.log((await c.verify(proof)).ok);  // true
Rust 
use serde_json::json;
use tinyzkp::{HcClient, TemplateProveOptions};

#[tokio::main]
async fn main() -> Result<(), tinyzkp::Error> {
    let c = HcClient::new("https://api.tinyzkp.com").with_api_key("tzk_...");
    let job = c.prove_template(
        "accumulator_step",
        json!({"initial":1000,"final":1045,"deltas":[10,20,15]}),
        TemplateProveOptions::default(),
    ).await?;
    let proof = c.wait_for_proof(&job, None).await?;
    assert!(c.verify(&proof, true).await?.ok);
    Ok(())
}

API Versioning & Deprecation

Production API and MCP releases expose release identity so operators can detect skew during a coordinated deploy. Use GET https://api.tinyzkp.com/version, GET https://mcp.tinyzkp.com/version, and GET https://tinyzkp.com/api/release when validating that docs, SDK examples, API behavior, and MCP tools are on the same revision. The public changelog and release policy defines when TinyZKP must publish migration notes for API, MCP, verifier, schema, template, pricing, and trust-surface changes.

  • New response fields are additive by default; clients should ignore fields they do not understand.
  • Route removals, required-parameter changes, proof-format floors, and verifier acceptance changes require a changelog entry and migration guidance before public rollout unless the change is an emergency security disablement.
  • Deprecated routes or fields receive at least one release cycle of warning where security permits. Proof-format deprecations also document the verifier package and compatibility floor.

Parameters

Transparent vs Privacy Mode

The current self-serve templates issue transparent STARK state-transition receipts. That means the template parameters needed to verify the statement are public. Experimental masking parameters such as zk_mask_degree are not a buyer-facing privacy claim unless the configuration is explicitly supported, documented, and reviewed.

  • Use transparent receipts for public balances, counters, audit-log checkpoints, and reconciliations where verifiers need to inspect the statement.
  • Use the contact form before claiming hidden-input privacy, regulated-data handling, or custom proof statements.
  • Default production verification accepts the documented receipt format and rejects legacy proof formats unless an explicit compatibility path is enabled.

Cost Estimation

Estimate trace length, base proof rate, proving time, and proof size before generating a proof. This endpoint is public — no authentication required. The response is an engineering estimate; plan discounts, included Free receipts, spend caps, and Compute recommendations are applied by the billing and calculator layers.

curl 
# Estimate cost for an accumulator_step proof
curl -X POST https://api.tinyzkp.com/estimate \
  -H "Content-Type: application/json" \
  -d '{
    "template_id": "accumulator_step",
    "params": {"initial": 1000, "final": 1045, "deltas": [10, 20, 15]}
  }'

Response:

{
  "estimated_trace_length": 128,
  "tier": "Tiny",
  "estimated_cost_cents": 5,
  "estimated_time_ms": { "min": 50, "max": 200 },
  "estimated_proof_size_bytes": { "min": 7000, "max": 15000 }
}
  • No auth required — use this to preview a base proof-rate estimate without an API key.
  • You can also estimate by program length: {"program_length": 500}.
  • The tier field is a legacy API rate-band label (Tiny, Standard, Large, Enterprise, or XL). It is not a storefront plan. Use estimated_trace_length, pricing metadata, and the pricing calculator for buyer-facing plan selection.

Batch Proving

Submit 1–100 prove jobs in a single request. Each job is billed individually by trace length. Each entry in requests is a full ProveRequest — pass template_id + template_params to use a built-in template, and always include initial_acc, final_acc, block_size, and fri_final_poly_size.

curl 
curl -X POST https://api.tinyzkp.com/prove/batch \
  -H "Authorization: Bearer tzk_..." \
  -H "Content-Type: application/json" \
  -d '{
    "requests": [
      {
        "template_id": "accumulator_step",
        "template_params": {"initial": 1000, "final": 1045, "deltas": [10, 20, 15]},
        "initial_acc": 0, "final_acc": 0, "block_size": 8, "fri_final_poly_size": 4
      },
      {
        "template_id": "accumulator_step",
        "template_params": {"initial": 500, "final": 575, "deltas": [25, 50]},
        "initial_acc": 0, "final_acc": 0, "block_size": 8, "fri_final_poly_size": 4
      },
      {
        "template_id": "accumulator_step",
        "template_params": {"initial": 0, "final": 100, "deltas": [40, 60]},
        "initial_acc": 0, "final_acc": 0, "block_size": 8, "fri_final_poly_size": 4
      }
    ]
  }'

Response:

{
  "job_ids": [
    "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "b2c3d4e5-f6a7-8901-bcde-f23456789012",
    "c3d4e5f6-a7b8-9012-cdef-345678901234"
  ]
}
  • Job IDs are returned in the same order as the requests (UUIDs).
  • Atomic rate limiting — if the batch would exceed your RPM quota, the entire batch is rejected (no partial submission).
  • Maximum batch size: 100 requests.
  • Poll each job individually via GET /prove/:job_id (status will be pending → running → succeeded/failed).

Proof Inspection

Get a detailed breakdown of a completed proof, including trace metadata, commitment digests, and verification timing.

curl 
curl https://api.tinyzkp.com/prove/JOB_ID/inspect \
  -H "Authorization: Bearer tzk_..."

Response:

{
  "trace_commitment_digest": "a1b2c3d4...",
  "initial_acc": 0,
  "final_acc": 42,
  "trace_length": 128,
  "query_commitments": {
    "trace_commitment": "a1b2c3d4...",
    "composition_commitment": "e5f6a7b8...",
    "fri_commitment": ""
  },
  "commitment_scheme": "STARK",
  "version": 5,
  "verify_time_ms": 3
}
  • The proof must be completed before inspection is available (returns 409 if still proving).
  • commitment_scheme is "STARK" for standard proofs.
  • allow_legacy_v2 exists only for explicit legacy verification and should not be enabled for new production receipt paths.
  • verify_time_ms is the server-side verification time, useful for benchmarking.

Production self-hosting checklist

  • Front the API with TLS, origin firewalling, and request-size limits.
  • Configure tenant keys, plan limits, proof timeouts, monthly caps, and abuse controls.

  • Install the monitoring probes for /healthz, /readyz, /templates, MCP server-card discovery, and a periodic proof/verify canary.
  • Follow the Hetzner, Cloudflare, incident-response, and release-policy docs before accepting live users.

Glossary

Key terms used throughout this documentation, explained in plain English.

TermWhat It Means
proofA short piece of data that proves a computation was done correctly. Anyone can verify it quickly, without re-running the computation.
paramsThe public template inputs for the current self-serve receipt. For accumulator_step, these are initial, final, and deltas.
traceThe step-by-step record of a computation. Each instruction the prover executes creates a row in the trace. A longer trace = more computation = higher cost.
trace_lengthHow many steps the computation has. This determines the proof-rate band and Compute estimate; buyer-facing plan selection still depends on volume, discounts, caps, and verifier visibility.
templateA pre-built proof program for a common use case (e.g., state-transition / accumulator proofs). Templates handle all the complexity — you just provide parameters. More proof types are in development.
zk_mask_degreeExperimental protocol v6 masking parameter. Default (0) = transparent receipt. Use privacy language only for configurations that are explicitly supported, documented, and reviewed.
block_sizeInternal parameter controlling how the trace is divided into chunks. The API sets this automatically — you almost never need to change it.
FRIFast Reed–Solomon Interactive Oracle Proof of Proximity. The core cryptographic protocol TinyZKP uses. You don’t need to understand it to use the API.
lde_blowup_factorControls how much the trace is expanded for error detection. Higher = stronger security but larger proofs. Default (2) is fine for most use cases.
initial_acc / final_accThe starting and ending accumulator values of a computation. For templates, these are set automatically from your parameters. For raw programs, they define the expected input→output.
STARKScalable Transparent ARgument of Knowledge. The type of proof system TinyZKP uses. “Transparent” means no trusted setup ceremony is needed. “Scalable” means verification is fast regardless of computation size.

Research Lineage

TinyZKP has two public repositories because the company evolved from an earlier KZG/BN254 research prototype into the current STARK product. The canonical production repo is logannye/hc-stark. The older space-efficient-zero-knowledge-proofs repo is research lineage and paper context, not the hosted TinyZKP engine.

The practical distinction is simple: TinyZKP's hosted receipt path uses transparent STARK-style verification with no trusted setup ceremony. The older repo explores sublinear-space proving with KZG commitments over BN254 and therefore has a different trust and deployment model.
