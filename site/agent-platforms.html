For agent platforms

Make proof receipts a native capability in every agent runtime.

Agent platforms are becoming the control plane for tool calls, approvals, records, money movement, and workflow state. TinyZKP gives those platforms a narrow, installable proof layer: when an agent changes important state, it can return a receipt another system can verify without trusting the transcript or replaying the backend.

The platform wedge

Agents already know how to call tools. The missing primitive is a standard artifact that says which durable state changed and lets another party check the encoded transition. TinyZKP should be exposed as a platform capability, not a cryptography project every app team has to reimplement.

Agent IDEs

Developer-visible receipts

Attach receipts to code-modifying, deployment, data-migration, or record-changing agent actions so reviews include a checkable artifact.

Workflow engines

Checkpoint every consequential batch

Mint receipts after approvals, reconciliations, inventory updates, ticket automations, and long-running job checkpoints.

Agent marketplaces

Standard receipt behavior

Let platform users require proof receipts for specific tool categories: payments, records, permissions, quotas, and operational state.

Embed the receipt policy

Make proof behavior part of platform governance. Agents should not decide ad hoc when to produce evidence; the platform should route high-value mutations through a policy that is visible to developers and recipients.

When a tool changes durable state:
1. map the state change to a supported receipt statement
2. call TinyZKP through MCP or REST
3. attach receipt_url to the final agent output
4. store the proof job ID beside the workflow checkpoint
5. never put secrets or private customer data into transparent parameters

What platform users get

  • A receipt URL beside agent output.
  • A consistent envelope for downstream systems.
  • Free verification for customers, auditors, and other agents.
  • Clear boundaries around what was encoded and what was not.

What platform owners get

  • A differentiated trust feature for high-value actions.
  • Policy knobs for when receipts are required.
  • Spend caps and throughput tiers for rollout control.
  • A pilot path for custom state machines or private-input review.

The commercial route for platforms

Platform adoption should not start as an undifferentiated API checkout. Start with one receipt-required category, prove the policy and verifier path, then launch the native platform surface with a supportable commercial model.
