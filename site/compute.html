What is live now on Compute

Self-serve Compute is for long accumulator and state-transition traces. The production path uses TinyZKP's transparent STARK receipt model and the same portable proof object as the rest of the hosted service. It is not the older KZG/BN254 research prototype, and it is not a blanket promise that zkVM, zkML, or rollup proving are generally available.

  • Live: long state-transition receipts up to the published single-proof cap.
  • Design-partner: custom state machines and very large traces that need sizing before production use.
  • Roadmap: zkVM, zkML, and rollup batch proving as supported self-serve products.

The structural advantage, in numbers

Computation size (N) Conventional STARK — O(N) TinyZKP — O(√N)
1M steps10–20 GB RAM~30 MB
10M steps100+ GB RAM~100 MB
100M stepsFleet sharding required~300 MB

The trade-off is honest: extra time for less memory. We pay roughly √N more cycles to use √N less RAM. For large computations, this trade-off is the only one that matters — RAM is the wall you hit first, and recovering memory unlocks workloads that conventional provers simply cannot run on commodity hardware.

Measured, not just asymptotic

In a reproducible sweep, the streaming commitment's peak working set stays ~0.04 MB as the trace grows to 16.7M elements, while the conventional O(N) path climbs to 513 MB — a √N (≈4,096×) reduction at the identical Merkle root (~1.2× the time). That height-compression is what bounds the full prover's memory in the table above. Re-run it: ./scripts/bench/run_sqrt_sweep.sh — numbers + method in docs/benchmarks/sqrt_memory_scaling.md.

At modest trace sizes the dollar savings are real but moderate — the bigger win is that there's no prover fleet to operate and nothing to re-run to verify. The savings widen sharply on a single very large trace (100M+ steps), where a conventional O(N) prover needs a 512 GB+ box or a recursion pipeline and TinyZKP's O(√N) prover does not. Honest trade-off: the streaming prover uses ~√N more compute to use ~√N less memory, so very large traces take longer — talk to us before relying on a single 100M-step proof under the per-job time cap.

The technical claim, stated carefully

TinyZKP is a STARK proving service designed around O(√N) prover memory for supported state-transition workloads, which lets a 100M-step trace fit on commodity hardware. Most STARK systems require O(N) memory — linear in computation size — forcing aggressive segmentation+recursion or simply capping trace size. The whitepaper and benchmarks document the memory claim; the open-source backend ships the current receipt path; the Compute tier is the usage-based access point.
